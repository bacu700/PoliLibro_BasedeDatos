1.1. Elementos


El Contenedor de Datos
Tablas (Entidades): Es la unidad básica donde se guarda la información. Piensa en ellas como pestañas de un archivo Excel (ej. una tabla de "Clientes", otra de "Productos").
Campos (Columnas/Atributos): Definen qué tipo de dato se va a guardar. Si la tabla es "Clientes", los campos serían "Nombre", "Correo" o "Teléfono".
Registros (Filas/Tuplas): Es una unidad individual de datos. Siguiendo el ejemplo, una fila completa con los datos de "Juan Pérez" es un registro.

Las Llaves (Identificadores)
Para que la base de datos sea eficiente y no haya confusiones, usamos "llaves":
Llave Primaria (Primary Key): Es un código único que identifica a un registro y no se puede repetir. Por ejemplo, tu número de identificación oficial o un ID de cliente (ID_001).
Llave Foránea (Foreign Key): Es una llave primaria de una tabla que aparece en otra tabla para conectarlas. Sirve para decir: "Este pedido (en la tabla Pedidos) pertenece a este Cliente (en la tabla Clientes)".

Esquemas y Relaciones
Esquema: Es el mapa o diseño lógico de toda la base de datos. Muestra cómo se conectan todas las tablas entre sí.
Relaciones: Definen cómo interactúan los datos. Pueden ser: Uno a muchos: Un cliente puede tener muchos pedidos. Muchos a muchos: Muchos estudiantes pueden inscribirse en muchos cursos diferentes.

1.1.1. Ambiente de bases de datos e historia del manejo de información

El Ambiente de las Bases de Datos

Un "ambiente" de base de datos no es solo el software donde se guardan los datos, sino un ecosistema compuesto por cinco componentes que trabajan en conjunto:
Hardware: Los servidores, discos de almacenamiento y memoria RAM donde reside la información física.
Software (DBMS): El Sistema de Gestión de Bases de Datos (como MySQL, Oracle o SQL Server) que actúa como interfaz entre el usuario y los datos físicos.
Datos: El recurso más valioso. Incluyen los datos operativos y los metadatos (datos sobre los datos, como diccionarios de datos).
Procedimientos: Las reglas y normas que rigen cómo se capturan, aseguran y respaldan los datos.

Usuarios:

  • DBA (Administrador): Responsable de la salud y seguridad del sistema.
  • Diseñadores: Quienes crean la estructura de las tablas.
  • Usuarios finales: Quienes consultan la información para tomar decisiones.

Historia del Manejo de Información:

    A. La Era Manual (Pre-1950) Antes de las computadoras, la información se gestionaba en archivos físicos (papel y carpetas). Problema: La redundancia era masiva, el acceso era lentísimo y era imposible cruzar datos de diferentes departamentos de forma eficiente.

    B. El Modelo de Archivos Planos (1950 - 1960) Con la llegada de las primeras computadoras, los datos se guardaban en cintas magnéticas. Características: Eran "archivos planos" (como un bloc de notas gigante). Limitación: Si querías leer el dato final, tenías que recorrer toda la cinta desde el inicio (acceso secuencial). No había relación entre archivos.

    C. El Modelo Jerárquico y de Red (1960 - 1970) Para mejorar el acceso, se crearon estructuras más complejas: Jerárquico: Los datos se organizaban como un árbol genealógico (un padre, muchos hijos). Red: Similar al jerárquico, pero un "hijo" podía tener varios "padres". Falla: Eran sistemas muy rígidos; si querías cambiar la estructura, tenías que reprogramar casi todo el sistema.

    D. La Revolución Relacional (1970 - Actualidad) En 1970, Edgar F. Codd (investigador de IBM) publicó un modelo basado en la teoría de conjuntos: el Modelo Relacional. Hito: Propuso que los datos se guardaran en tablas simples y se relacionaran mediante llaves. SQL: En los 80, SQL se convirtió en el estándar, permitiendo que cualquier persona con conocimientos básicos pudiera consultar datos complejos.

    E. La Era Post-Relacional y Big Data (2000 - Presente) Con el auge de redes sociales y sensores, el modelo de tablas ya no era suficiente para todo. NoSQL: Surgen bases de datos no relacionales para manejar datos no estructurados (como documentos, videos o grafos). Cloud Databases: La transición a la nube, donde la escalabilidad es casi infinita.

1.1.2. Ambiente de informacion con Sistemas de archivos y con tecnologia de Bases de Datos

Ambiente con Sistemas de Archivos (El Enfoque Tradicional)

    Antes de que existieran los sistemas de bases de datos centralizados, las empresas desarrollaban software donde cada aplicación o departamento de la empresa era dueño de sus propios archivos de datos. Por ejemplo, el departamento de Ventas tenía su propio archivo de "Clientes.txt" y el departamento de Facturación tenía su propio archivo "Facturas.dat".

El enfoque generaba varios problemas:

  • Redundancia de Datos: Como los sistemas estaban separados, los mismos datos se duplicaban. El nombre y dirección de un cliente podían estar guardados en tres archivos diferentes de tres departamentos distintos.
  • Inconsistencia de Datos: Si el cliente cambiaba de domicilio, Ventas podía actualizar su archivo, pero Facturación seguía usando la dirección vieja. Los datos dejaban de ser confiables.
  • Dependencia Estructura-Programa: El formato físico de los datos (cómo estaban ordenados los bytes en el disco) estaba escrito directamente dentro del código del programa. Si querías añadir un campo nuevo (por ejemplo, el código postal), tenías que modificar y reinstalar todos los programas que usaran ese archivo.
  • Falta de Compartición: Era extremadamente difícil que un departamento consultara de forma segura o rápida los datos de otro.

    • Ambiente con Tecnología de Bases de Datos (El Enfoque Moderno)

    Este enfoque cambia por completo la filosofía: en lugar de que cada aplicación tenga sus propios archivos, todos los datos de la organización se centralizan en un único repositorio lógico, el cual es administrado exclusivamente por el DBMS (Sistema de Gestión de Bases de Datos). Las aplicaciones ya no tocan los archivos directamente; le piden los datos al DBMS a través de un lenguaje estándar (como SQL).

    Ventajas y Elementos Clave:

  • Independencia de Datos: La estructura física de los datos está separada de los programas de aplicación. Puedes añadir columnas o cambiar el tipo de almacenamiento en el disco sin romper el software que usan los empleados.
  • Redundancia Mínima y Controlada: Cada dato se guarda, idealmente, en un solo lugar. Si el cliente cambia su dirección, se actualiza en una sola tabla y el cambio se refleja instantáneamente para toda la empresa.
  • Integridad y Seguridad Centralizada: El DBMS se encarga de aplicar las reglas de negocio (ej. "ningún salario puede ser menor a cero") y los permisos de acceso (ej. "Ventas no puede ver los datos de Recursos Humanos") en un solo punto de control.
  • Acceso Concurrente: Permite que miles de usuarios y aplicaciones lean y escriban datos al mismo tiempo sin bloquearse mutuamente ni corromper la información.

    • 1.1.3. Aspetos basicos de Bases de Datos Software de bases de datos Relacionales y No-SQL.

    Cuando diseñamos o administramos una arquitectura de datos, la primera gran decisión es elegir entre el modelo Relacional (SQL) y el modelo No-Relacional (No-SQL).

    Software de Bases de Datos Relacionales (RDBMS / SQL).

    Se basan en el modelo relacional matemático. Toda la información se organiza en estructuras rígidas y bidimensionales: las tablas..

    Figura 3. Ejemplo de una base de datos relacional

    Aspectos Básicos:

  • Esquema Estricto (Predefinido): Antes de insertar un solo dato, debes definir la estructura exacta: qué tablas existen, qué columnas tienen y qué tipo de dato acepta cada una (entero, texto, fecha).
  • Lenguaje Estándar: Utilizan SQL (Structured Query Language) para realizar consultas, inserciones y modificaciones.
  • Propiedades ACID: Es su mayor fortaleza. Garantizan que las transacciones sean seguras y confiables:
    1. Atomicidad: O se hace toda la operación o no se hace nada.
    2. Consistencia: Los datos siempre son válidos según las reglas del sistema.
    3. Aislamiento: Las operaciones concurrentes no se estorban entre sí.
    4. Durabilidad: Una vez guardado el dato, no se pierde ni ante un apagón.
    5. Escalabilidad Vertical: Para soportar más carga, generalmente requieren un servidor más potente (más CPU, más RAM).

    Software de Bases de Datos No-Relacionales (No-SQL).

    Nacieron a principios de los años 2000 para resolver los problemas de almacenamiento masivo y alta velocidad que el modelo relacional no podía manejar eficientemente (el fenómeno del Big Data y la web en tiempo real).

    Aspectos Básicos:

  • Esquema Flexible (Dinámico): No requieren una estructura fija. Un registro puede tener tres campos y el siguiente puede tener diez, sin necesidad de alterar la base de datos.
  • Sin Joins Complejos: Evitan las relaciones complejas entre tablas para ganar velocidad. En su lugar, los datos suelen estar "desnormalizados" (guardados juntos en el mismo sitio).
  • Teorema de CAP / Propiedades BASE: En lugar de la rigidez de ACID, priorizan la disponibilidad y la velocidad, aceptando una "consistencia eventual" (los datos se actualizarán en todos los servidores un poco más tarde, pero el sistema nunca se detiene).
  • Escalabilidad Horizontal: Diseñadas desde cero para distribuirse en decenas o cientos de servidores económicos en la nube.

    1.1.4. Ambiente y ventajas de los sistemas de información con tecnología de Bases de Datos

    La adopción de la tecnología de bases de datos dentro de los sistemas de información empresariales no solo optimiza el almacenamiento físico, sino que transforma la información en un activo estratégico disponible en tiempo real para la toma de decisiones.

    Ventajas organizacionales y técnicas:

    • Compartición de datos global: Múltiples aplicaciones y usuarios de distintos departamentos acceden simultáneamente al mismo repositorio lógico de datos.
    • Estandarización de estructuras: Se unifican los formatos de captura, codificación y almacenamiento de la información en toda la organización.
    • Flexibilidad ante el cambio: Facilidad para añadir nuevas entidades o campos de información sin la necesidad de reescribir por completo las capas funcionales del software de aplicación.
    • Reducción de costos de mantenimiento: Al centralizar la lógica de persistencia, los esfuerzos informáticos se concentran en optimizar un único entorno en lugar de decenas de archivos dispersos.

    1.1.5. Esquemas de la arquitectura de las bases de datos relacionales

    Para lograr la independencia de datos y el aislamiento operativo, el estándar de la arquitectura de bases de datos se basa en el modelo de tres niveles de abstracción propuesto por el comité ANSI/SPARC. Este diseño jerárquico separa la visión que tiene el usuario final de los datos de cómo se guardan físicamente en las unidades de disco.

    Niveles de la Arquitectura ANSI/SPARC

    • Nivel Externo (Vistas de Usuario): Es el nivel más cercano al usuario. Describe cómo perciben los datos los distintos perfiles de la organización (por ejemplo, el cajero solo ve saldos, mientras que el auditor ve historiales de transacciones completos).
    • Nivel Conceptual: Representa la estructura lógica global de toda la base de datos administrada. Describe qué datos se almacenan y qué relaciones e integridades existen entre ellos, abstrayendo por completo el hardware.
    • Nivel Interno (Físico): Es el nivel más bajo de abstracción. Define cómo se organizan físicamente los datos en los discos, detallando los tamaños de registro, los mecanismos de indexación, las rutas de directorios y la compresión de bytes.


    1.2. El análisis y diseño de bases de datos

    El Análisis y Diseño de Bases de Datos es la fase más crítica de cualquier proyecto de software o sistemas de información. Si esta etapa se hace mal, el sistema final será lento, tendrá errores de datos y modificarlo en el futuro será una pesadilla. Este proceso transforma los requerimientos de un negocio (lo que el usuario necesita) en una estructura técnica y optimizada dentro de un disco duro.

    1.2.1. Ingeniería de Software

    Llegamos al terreno que une todo lo anterior. La Ingeniería de Software es la disciplina que aplica métodos, herramientas y técnicas estructuradas para construir software de calidad, a tiempo y dentro del presupuesto. Cuando conectamos la Ingeniería de Software con las Bases de Datos, pasamos de simplemente "crear tablas" a integrar esas bases de datos dentro de un ciclo de vida completo de un sistema..

    1.2.2. Ciclo de vida de sistemas

    Cualquier sistema de información empresarial pasa por un proceso de evolución ordenado conocido como el Ciclo de Vida del Desarrollo de Sistemas (SDLC). Esta metodología asegura que el software cumpla de forma rigurosa con los objetivos del negocio antes de pasar a su fase de operación.

    Etapas generales del ciclo de vida:

    1. Investigación Preliminar y Viabilidad: Determinación de los alcances lógicos, costos financieros y factibilidad tecnológica del proyecto.
    2. Análisis de Sistemas: Estudio detallado de los procesos de negocio actuales para documentar qué es lo que el nuevo sistema debe resolver de forma estricta.
    3. Diseño de Sistemas: Modelado técnico detallado que incluye la arquitectura del software, las interfaces de usuario y los diagramas lógicos de datos.
    4. Desarrollo e Implementación: Codificación física de los módulos de la aplicación, construcción de las tablas en el DBMS y pruebas exhaustivas de integración.
    5. Mantenimiento y Evolución: Corrección de fallos operativos en producción e incorporación de nuevas funcionalidades solicitadas por los usuarios.

    1.2.3. Ciclo de vida relacionado al modelado de BDs

    Es una ruta estructurada que se sigue dentro de la Ingeniería de Software para transformar una idea o necesidad de negocio en una estructura de datos real, funcional y optimizada. Este ciclo de vida no es un evento único; es un proceso iterativo que acompaña a todo el sistema desde su nacimiento hasta su retiro. A continuación se detallan cada una de sus etapas:.

    Planificación y Definición del Sistema
    Antes de modelar, se debe entender el alcance del proyecto. En esta etapa se responde a la pregunta: ¿Qué parte del mundo real vamos a digitalizar?

  • Identificación de Fronteras: Se delimita qué procesos de la organización afectarán a la base de datos (por ejemplo, el área de facturación e inventarios, pero dejando fuera recursos humanos).
  • Análisis de Factibilidad: Se evalúan los costos, el tiempo y la tecnología necesaria para soportar el volumen de datos esperado.

    • Análisis de Requerimientos (Recolección de Datos)
    Aquí se recopila toda la información sobre cómo opera el negocio. El modelador actúa como un "traductor" entre los usuarios de la empresa y el lenguaje técnico.

  • Fuentes de información: Se analizan formatos físicos (facturas en papel, hojas de Excel), se realizan entrevistas con los empleados y se estudian las reglas del negocio.
  • Entregable: Un documento de especificación de requerimientos que detalla los datos que se deben almacenar y las restricciones que se deben aplicar (por ejemplo, "Un cliente no puede tener más de un crédito activo a la vez").

    • Modelado Conceptual (Abstracción)
    Es la primera representación gráfica de los datos. El objetivo es plasmar el conocimiento del negocio sin pensar todavía en la tecnología o el software que se usará.

  • Enfoque: Es un modelo de alto nivel, puramente semántico. Debe ser entendible tanto por los programadores como por los directivos de la empresa.
  • Herramienta estándar: El Diagrama Entidad-Relación (DER) básico, donde se identifican las Entidades principales (rectángulos) y cómo se conectan entre sí a través de Relaciones (rombos).

    • Modelado Lógico (Estructuración)
    En esta fase, el modelo abstracto se adapta al paradigma de base de datos elegido (generalmente el Modelo Relacional).

  • Transformación: Las entidades del mapa conceptual se convierten en estructuras de tablas. Se definen formalmente los tipos de columnas, las Llaves Primarias (PK) y las Llaves Foráneas (FK).
  • Normalización: Es un paso obligatorio en esta etapa. Se aplican las reglas matemáticas de normalización (Primera, Segunda y Tercera Forma Normal) para asegurar que no haya duplicación de datos y evitar problemas al insertar o borrar información.
  • Independencia del software: El modelo lógico especifica tablas y relaciones, pero sigue siendo independiente de si usarás MySQL, Oracle o PostgreSQL.

    • Modelado Físico (Implementación)
    Aquí el modelo lógico se traduce al código que el motor de base de datos (DBMS) específico puede entender y ejecutar.

  • Definición de Tipos de Datos: Se asignan los tipos de datos exactos según el software elegido (por ejemplo, INT, VARCHAR(255), DATETIME).
  • Optimización de Rendimiento: Se crean índices para acelerar las búsquedas frecuentes, se configuran particiones de disco y se establecen las reglas de seguridad físicas.
  • Entregable: El script de código DDL (Data Definition Language) lleno de sentencias CREATE TABLE listo para ser ejecutado en el servidor.

    • Pruebas y Validación
    Una vez creada la estructura en el servidor de desarrollo, se debe verificar que soporte las operaciones reales de la aplicación.

  • Poblamiento Inicial: Se introducen datos de prueba (datos ficticios pero realistas).
  • Pruebas de Estrés y Carga: Se simulan miles de consultas simultáneas para comprobar el tiempo de respuesta del servidor y detectar cuellos de botella.
  • Validación de Reglas: Se comprueba que las restricciones (constraints) funcionen (por ejemplo, intentar meter un usuario sin correo para verificar que el sistema lo rechace correctamente).

    • Operación y Mantenimiento (Evolución)
    La base de datos entra en producción y empieza a recibir datos reales de los usuarios. Esta fase dura toda la vida útil del sistema.

  • Monitoreo: El Administrador de la Base de Datos (DBA) vigila el rendimiento, el crecimiento del espacio en disco y realiza respaldos (backups) periódicos.
  • Gestión de Cambios (Migraciones): Las empresas evolucionan, lo que significa que el modelo de datos también debe hacerlo. Si el negocio pide una nueva funcionalidad, el modelo debe regresar a la fase de análisis y diseño para agregar nuevas tablas o columnas sin romper lo que ya está funcionando.

    • 1.2.4. Métodos, herramientas, procedimientos y su relación al ciclo de vida de un sistema

    Para ejecutar con éxito cada fase del ciclo de vida de un sistema de información, los ingenieros de software se apoyan en un ecosistema integrado de elementos metodológicos:

    • Métodos: Son los enfoques estructurados o ágiles (como Scrum, Cascada o DevOps) que dictan la secuencia de pasos y las pautas técnicas para avanzar a través del desarrollo del sistema.
    • Herramientas (CASE): Aplicaciones automatizadas de ingeniería asistida por computadora (como modeladores UML, entornos IDE de desarrollo y herramientas de control de versiones como Git) que aceleran la documentación y diseño.
    • Procedimientos: Reglas organizacionales escritas y controles de calidad aplicados para validar que cada entregable cumpla con los estándares de seguridad e integridad definidos por la empresa.
