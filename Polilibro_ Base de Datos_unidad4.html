4.1. Bases de datos NoSQL

 


El movimiento NoSQL (Not Only SQL) ha demostrado una enorme utilidad en la ingeniería de software moderna para resolver las limitaciones del modelo relacional tradicional frente al almacenamiento de grandes volúmenes de datos distribuidos, heterogéneos y de alta velocidad. A través de arquitecturas horizontales y esquemas flexibles, estas soluciones permiten modelar y hacer la representación visual de la persistencia de datos en aplicaciones de alta escala.


Figura 16. Tipologías de Bases de Datos NoSQL

Las bases de datos NoSQL tienen la finalidad de modelar los requerimientos funcionales de almacenamiento masivo, tomando en cuenta las acciones de lectura y escritura concurrentes que los usuarios ejecutarán al utilizar el sistema. Por lo tanto, este enfoque de almacenamiento permite visualizar y optimizar el comportamiento que el motor de datos debe ejecutar bajo cargas intensas.

Los beneficios que se tienen al seleccionar e implementar una base de datos NoSQL están orientados a: la comprensión precisa de la escalabilidad, muestra una composición altamente modular del almacenamiento, ayuda al desarrollo evitando la rigidez de un esquema fijo y aporta una mayor productividad en sistemas que manejan datos semiestructurados o no estructurados, generando un sistema robusto que cubre los requerimientos de la era del Big Data. En los siguientes temas se puntualiza en sus modelos principales.

4.1.1. Bases de datos clave-valor: Características, arquitectura y modelo

El almacenamiento Clave-Valor representa el modelo NoSQL más simplificado y eficiente en términos de velocidad. Basado en una representación directa, asocia un identificador único (clave) con un bloque de datos indeterminado (valor), el cual es completamente transparente para el motor de la base de datos. Esta técnica se utiliza en arquitecturas de alta disponibilidad, permitiendo una rápida recuperación y un nivel de abstracción mínimo en el procesamiento de peticiones.

Para implementar un diseño clave-valor eficaz, se parte de la información transaccional proporcionada por los procesos del sistema. Durante el análisis del flujo de datos, se configuran colecciones de datos donde el acceso se realiza exclusivamente a través de su clave indexada, optimizando al máximo operaciones críticas como el manejo de sesiones de usuario o carritos de compra.

La arquitectura de este modelo se clasifica por su capacidad de operar directamente en memoria RAM o con persistencia ligera en disco. El modelo lógico está compuesto por diccionarios distribuidos simples, asegurando que los tiempos de respuesta se mantengan constantes sin importar que la base de datos crezca exponencialmente de tamaño.

Por otro lado, el modelado físico corresponde al despliegue en nodos distribuidos (clústeres). Esto se gestiona con algoritmos de particionamiento como el hashing consistente, que mapea las llaves uniformemente a través de múltiples servidores para garantizar tolerancia a fallos.

Como recordarás, en los sistemas tradicionales la consistencia rígida (ACID) limitaba la velocidad; el modelo clave-valor adopta en su lugar el teorema de CAP, priorizando la disponibilidad y la tolerancia a la partición.

4.1.2. Bases de datos documentales: Características, arquitectura y modelo

Una excelente práctica en el desarrollo de sistemas con requerimientos de esquemas cambiantes es el uso del almacenamiento documental. Es una evolución del modelo clave-valor donde el "valor" no es un bloque opaco, sino un documento estructurado con una nomenclatura semántica estándar.

Este diagrama lógico permite identificar cada entidad de forma independiente, codificando la información comúnmente en formatos legibles como JSON (JavaScript Object Notation) o BSON. Esto significa que el propio motor de la base de datos puede inspeccionar el contenido del documento, permitiendo realizar indexaciones internas y búsquedas complejas por cualquier campo secundario.

Los sistemas documentales se componen principalmente de tres elementos esenciales: las colecciones, los documentos y los identificadores únicos (IDs).

Las colecciones representan conjuntos de documentos con un propósito similar en el negocio, pero sin la obligación de compartir exactamente las mismas columnas o campos. Considere como ejemplo un “Sistema de comprobación de gastos”: en un modelo relacional tradicional, si un empleado añade un tipo de comprobante imprevisto, la estructura completa de la tabla se rompería.


Figura 17. Documento JSON utilizado en CouchDB para representar la información del usuario y su dirección.


El documento en sí representa la fila o registro del negocio. Se caracteriza por su estructura de pares clave-valor anidados y árboles jerárquicos. Un caso de uso típico de este modelo es la gestión de perfiles complejos de usuarios, donde un solo documento almacena de forma embebida tanto la información básica del usuario como sus múltiples direcciones históricas, evitando la necesidad de realizar uniones físicas (JOINs) de tablas. 4.1.3. Bases de datos orientadas a columnas: Características, arquitectura y modelo

Las bases de datos orientadas a columnas (o de columnas anchas) en el paradigma NoSQL se utilizan para identificar patrones masivos y realizar agregaciones complejas en entornos analíticos (OLAP) y Big Data. Es una representación optimizada de cómo se organizan internamente los archivos en el almacenamiento físico, estructurando los datos en discos de forma contigua por columnas en lugar de por filas tradicionales.

Para comprender un diseño orientado a columnas se deben considerar los elementos estructurales que integran su modelo conceptual. La jerarquía de almacenamiento organiza la información desde familias de columnas lógicas hasta celdas individuales provistas de marcas de tiempo automáticas.

4.2. Software y lenguaje para implementar y usar bases de datos NoSQL

La implementación física de un sistema NoSQL requiere seleccionar las soluciones de software adecuadas que respondan lógicamente a las demandas operativas del proyecto. Cada tipo de motor cuenta con sus propios lenguajes de manipulación de datos (DML) adaptados a su arquitectura de consulta. Por ejemplo, en el entorno documental, los desarrolladores utilizan lenguajes declarativos basados en métodos fluidos u objetos de consulta, mientras que en los sistemas orientados a columnas se emplean variantes optimizadas similares a SQL (como CQL en Apache Cassandra), permitiendo realizar consultas eficientes de registros a través de claves de partición.
Los componentes que integran el software gestor NoSQL gestionan de manera automatizada la replicación entre nodos de un clúster y la consistencia eventual. El sistema físico pasa por transiciones de sincronización transparente en background, asegurando la resiliencia ante caídas de red.
